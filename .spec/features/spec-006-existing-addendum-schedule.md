# Корректировка графика по существующему соглашению — issue #19

Статус: сценарий и ограничения согласованы пользователем 24.11.2026;
реализация выполнена; полный `clean test` пройден 24.11.2026.
Дополняет `spec-005-ai-schedule-creation.md`.

## Цель

Запрос пользователя оформить корректировку отгрузок по существующему ДС №4
от 09.11.2026 должен создать полный снимок графика, связанный с этим ДС.
Пример снимка: 01.12.2026 — 100 000 руб. Базовый график остаётся прежним,
дубликат соглашения не создаётся. Аналогичное правило действует для платежей.

## Согласованная пользовательская история

1. Пользователь находит **дополнительное соглашение №4 к контракту
   АО «НК НПЗ» 3281126/0222Д**, дата вступления в силу — **09.11.2026**.
   Помощник связывает черновик с ID этого существующего соглашения.
   Если у контракта несколько проектов, пользователь выбирает нужный проект.
2. Пользователь просит внести в рамках этого ДС корректировку отгрузок:
   **01.12.2026 — 100 000 руб.** Отсутствующий или пустой базовый график
   не меняет смысл запроса и не препятствует подготовке корректировки.
3. Помощник проверяет ограничения ниже и готовит предпросмотр:

   | Поле | Значение |
   | --- | --- |
   | Операция | Корректировка плана отгрузок |
   | Контракт | АО «НК НПЗ» 3281126/0222Д |
   | Проект | Выбранный проект контракта |
   | Дополнительное соглашение | №4, существующий документ |
   | Дата вступления в силу | 09.11.2026 |
   | Дата отгрузки | 01.12.2026 |
   | Сумма | 100 000 руб. |

   Предпросмотр также содержит сравнение с применимым прежним планом
   и явное пояснение: **это полный новый снимок плана отгрузок из одной
   строки, а не добавление строки к прежнему плану**. Если намерение
   пользователя неоднозначно, помощник уточняет его до публикации
   предложения на подтверждение.
4. После явного подтверждения актуального предложения создаётся одна
   корректировка плана отгрузок с одной строкой, связанная с существующим
   ДС №4 и выбранным проектом. Реквизиты ДС и базовый график не меняются;
   новый документ ДС не создаётся. Повтор подтверждения не создаёт дубликатов.
5. С 09.11.2026 при расчёте актуального плана применяется этот снимок;
   до этой даты применяется прежний план. Дата вступления ДС в силу
   и дата отгрузки 01.12.2026 имеют разные назначения и не подменяют друг друга.
   Сообщение об успехе формируется после успешной записи и идентифицирует
   корректировку и существующее ДС №4.

## Согласованные ограничения истории

Проверки выполняются для **выбранного проекта и типа графика** (в этой
истории — отгрузок), включая будущие и пустые корректировки:

- Если в ДС №4 уже есть корректировка отгрузок этого проекта, запись
  запрещена, даже если корректировка не содержит строк. Помощник объясняет,
  что изменение уже существующей корректировки этим сценарием не поддерживается.
- Если есть корректировка отгрузок этого проекта с датой вступления в силу
  09.11.2026 или позднее, запись запрещена. Помощник объясняет конфликт
  истории; последующие снимки автоматически не пересчитываются.
- Корректировка платежей либо корректировка другого проекта сама по себе
  не является таким конфликтом.
- При любом отказе бизнес-данные не записываются. Помощник не переключается
  на создание, заполнение или замену базового графика и не выдаёт отказ
  за успешное сохранение.
- Если конфликты отсутствуют и проверки доступа пройдены, описанная история
  должна завершаться сохранением корректировки в существующем ДС №4.

## Рассмотренные подходы

1. Только запретить подмену операции в промпте. Это устраняет часть неверных
   ответов, но не обеспечивает требуемое сохранение в существующее ДС.
2. Добавить выбор существующего ДС по ID и серверную проверку всей операции.
   Это выбранный вариант: используется существующий механизм предпросмотра,
   подтверждения, блокировки контракта и атомарной записи.
3. Дополнительно разрешить замену корректировок и пересчёт последующей истории.
   Это требует самостоятельных правил редактирования истории и расширяет фикс.

## Требования к поведению

- Инструменты подготовки позволяют получить доступные соглашения выбранного
  контракта и выбрать существующее по ID. Номер и дата берутся с сервера.
- Черновик сохраняет ID соглашения и намерение корректировки. Правка строк,
  восстановление черновика и повторный предпросмотр не превращают это намерение
  в CREATE, FILL или REPLACE. Смена контракта сбрасывает неподходящий выбор ДС,
  но требует нового выбора соглашения, а не записи базового графика.
- Отсутствующий или пустой базовый график не препятствует созданию корректировки
  в выбранном существующем ДС при выполнении остальных проверок.
- Правило конфликтов: для выбранных проекта и типа графика
  запрещена запись, если в выбранном ДС уже есть корректировка, включая пустую,
  либо есть корректировка с такой же или более поздней датой. Ответ объясняет
  причину; замены документа и автоматического выбора другого режима нет.
- Проверяются доступность соглашения, принадлежность контракту, принадлежность
  проекта контракту, полнота доступной истории и права на создаваемую
  корректировку и строки. Существующие реквизиты ДС не изменяются.
- Перед сохранением проверки выполняются повторно под существующей блокировкой
  контракта. Изменившаяся история или права отменяют прежнее подтверждение.
- Предпросмотр показывает «Корректировка плана отгрузок» (либо платежей),
  контракт, проект, номер и дату ДС, полный снимок и изменения относительно
  применимого графика. Явно поясняется, что строки заменяют весь план начиная
  с даты ДС; неоднозначное «добавить строку» требует уточнения до предложения.
- Подтверждение пользователя по-прежнему связано с опубликованной версией
  предложения. Квитанция появляется только после commit, называет сохранённую
  корректировку и соглашение и открывает существующее ДС.
- Старые JSON-черновики без ID соглашения продолжают поддерживать создание
  нового ДС. Добавление поля не требует изменения доменной схемы БД.

## Проверки реализации

- Интеграционный сценарий issue #19: существующее ДС, одна строка, предпросмотр,
  реальное подтверждение, ровно одна корректировка, неизменный базовый график
  и прежнее количество соглашений; повтор подтверждения идемпотентен.
- Отсутствующий и пустой базовый график; оба типа графика; другое соглашение
  с более ранней корректировкой; существующее ДС без нужной корректировки.
- Отказы при чужом контракте, недоступном ДС, недостаточных правах,
  существующей пустой/заполненной корректировке и последующей истории.
- Сохранение намерения и ID при правке строк, перезагрузке и восстановлении;
  отклонение переключения на базовый график; совместимость старого JSON.
- Конкурентное изменение ДС/истории между предпросмотром и подтверждением;
  отсутствие бизнес-записей при отказе; точность текста предпросмотра и квитанции.
- Статическая проверка изменённых файлов и полный `./gradlew clean test`
  на отдельной тестовой БД с загрузкой Spring/Jmix-контекста.

## Границы

Замена уже существующих корректировок и изменение последующей истории
не входят в фикс. Причина конкретного прежнего сообщения
«Сохранено» требует доступа к той беседе и её данным; анализ кода сам по себе
не устанавливает, какой объект был записан в пользовательской базе.

## Попытка проверки живой модели — 24.11.2026

После явного разрешения пользователя выполнен отдельный live-прогон через
настроенный OpenWebUI `https://ai2mee.ru/api`, модель `gpt-4o-mini`, с ключом
из локального `.env` (значение ключа не публикуется). Использованы реальные
`ScheduleAiChatDataService` и инструменты приложения, без подмены ChatModel,
временный тест вне обычного source set и отдельная PostgreSQL-база
`finassist_issue19_live` с синтетическими данными.

Запланированы четыре сценария: заполненный, пустой и отсутствующий базовый
график, а также конфликт более поздней корректировки. Все четыре остановились
на первом запросе поиска ДС: сервис вернул **401 Unauthorized**, сообщение
«Your session has expired or the token is invalid. Please sign in again.».
Ответов модели и вызовов бизнес-инструментов не получено. Поэтому выбор
инструментов и прохождение сценария живой моделью остаются **непроверенными**.
Это отдельный отказ внешней авторизации, а не успешная live-проверка и не
падение одного из 489 тестов полного изолированного прогона.

Для повторения требуется действующий `OPENAI_API_KEY` OpenWebUI с доступом
к выбранной модели. Ключ не нужно передавать в переписке или коммитить.


Повторный live-прогон по указанию пользователя использовал параметры текущей
IntelliJ IDEA Run Configuration **Fin-assist Jmix Application**: `OPENAI_API_KEY`
прочитан непосредственно из локального `.idea/workspace.xml`, модель —
**qwen/qwen3.8-flash**. Значение ключа не сохранялось в тестовых исходниках,
спецификации или Git. В конфигурации IDEA нет `OPENAI_BASE_URL`, поэтому
использован штатный адрес приложения `https://ai2mee.ru/api`.

Результат повторного прогона: **4 tests, 4 failures**, все с одинаковым
`401 Unauthorized` на первом запросе, до получения ответа модели и вызовов
бизнес-инструментов. Сообщение сервиса: «Your session has expired or the token
is invalid. Please sign in again.». Проверка сценария живой моделью по-прежнему
заблокирована внешней авторизацией. Подмена модели, ключа или адреса другими
параметрами не выполнялась. Тестовая БД удалена после прогона; рабочая БД
не использовалась. PR остаётся Draft до успешного live-прогона.
